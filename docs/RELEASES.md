# Release stages

Every build carries all of Konium; features of later public releases are switched off and shown as planned
(greyed with "Planned", their documents opening to a notice, their controls disabled) until the release that
brings them, so each release goes out with every fix made by then. `src/core/release.ts` names the features and
their stages.

To cut the next release:

1. Raise `STAGE` in `src/core/release.ts`.
2. Add the stage's What's New entry below to `public/whats-new.json` as the build's version (first in the list),
   with the fixes made since, and update the smoke test's What's New counts. Take "AD" out of the entry's text
   wherever it can go (it isn't banned, but kept to where nothing else says it); the drafts below still have it.
3. Put the stage's lines back in `index.html` (featureList, fileFormat and the `<li>`s) and `public/llms.txt`.
4. Take the stage out of `tests/tools/smoke.py`'s planned-features section (it opens without `features=all`).

`?features=all` in the address (or localStorage `konium.features` = `all`) switches every feature on, to test.

Version control and team projects, in place of SVN (a page can't speak SVN; Git it can, and Altium Designer works with Git repositories too): a project opened from its folder is put under version control as a Git repository in that folder (every version on the computer, the folder usable with any Git tool), kept with the team either in Konium's store (konium.app/api/vcs: nothing to set up; a team's key made in the browser seals everything before it leaves, so the store can't read it; colleagues join with the key) or on the team's own Git server (GitHub, GitLab, Bitbucket, Gitea …, reached through Konium's relay at konium.app/api/git unless the server lets pages reach it). Project › Version Control: Add Project to Version Control, Commit Whole Project (and push), Update Whole Project (a fast-forward, or a merge file by file with the choice for files changed on both sides: mine, theirs, both), Push, History and Document History (open a version, restore it, export the project as it was), Repository Settings (move to another place, history and all); File › Open Project from Version Control; the Projects panel's marks; Preferences › Data Management › Version Control. Soft locks: Lock and Unlock (they tell the team, they don't stop anyone), let go when the file is pushed. Compare: two versions of a schematic or board side by side at the same place and zoom, the differences coloured (added green, removed red, changed amber, the rest dimmed) and listed, from Document History, the history's changed files and the Storage Manager.

## R16 (STAGE = 16): switched on from 26.177

Published as 26.177: its What's New entry is 26.177's in `public/whats-new.json`, everything since 26.171 (the last public release before) in one: the five analyses of a board, built while planned in 26.172 to 26.176 (`analysis` in `src/core/release.ts`), with two pictures from the demo board (the Power Analysis panel beside the copper coloured by voltage drop, the Thermal Analysis panel beside the board coloured by temperature) and a closing item that says what they are: estimates worked out in the browser, with what each leaves out in its User Guide section. Its site lines are a Features section (`website/site.mjs`: analysis), a line of the home page's list, and `public/llms.txt`. No Worker changed in this stage.

What is in it, in the order it was built:

1. DC power analysis (26.172): a supply net's voltage drop to each load with its return net's rise, current density, via currents, tracks and vias against IPC-2221, copper areas against a density limit; the copper coloured over the board; a report. From 26.177 a source with no pad on the return net leaves the return out and says so.
2. Board temperature (26.173): settled temperature from the parts' dissipation and the copper's own loss, the resistance's rise fed back, warm-up over time, junction temperatures from the parts' junction-to-board resistances.
3. An EMC rule check (26.174): tracks over gaps and splits and along edges of their reference, layer changes with no return path, decoupling distance, ground stitching against a twentieth of a wavelength.
4. Supply impedance (26.175): impedance against frequency with the source, the capacitors and the planes, plane resonances, a differential-mode conducted emission estimate.
5. A 2D field solver (26.176): impedance, delay and coupling from the cross-section: microstrip, embedded, stripline, pairs, coplanar grounds, solder mask, etched slope; the width for an impedance.

Left for a stage of its own, not begun: antennas, by 3D FDTD on WebGPU over the antenna and its ground (return loss, impedance, radiation pattern, gain and efficiency). WebGPU answers in the headless browser the tests use, so it can be checked here. Not feasible, and said so in the entry: airflow, common-mode noise, and the radiated emission of a whole board with its cables.

## R18 (STAGE = 18): switched on from 26.182, public as 26.184

Planned on 14 Nov as "Rapid Simulation" (sketch a circuit quickly and run it, woven into Konium Designer; what it is modelled on is in docs/PROVENANCE.md) and settled on 15 Nov as Live Simulation: a way of running any sheet, not a second schematic editor, on the simulator's own engine and models so that it and Mixed Sim give the same answers.

1. (26.181) The engine and the sheet:
   - src/sim/engine.ts: a transient with no end, taken a slice at a time (liveStart, liveAdvance, liveKick): the transient analysis's own stepping (truncation error, Newton, the sources' corners, found one at a time by nextSourceBreak so that an hour in costs what the first second did). A changed circuit starts from what the run held, by name (unknownsNow → liveStart's carry).
   - src/sim/adNetlist.ts: for a live run the netlist meters every pin: a 0 V source between the pin's net and a node of the pin's own. Its current is the current into the part at that pin, whatever the part is made of (a subcircuit too). LiveMap says which node is each net's and which meter each pin's.
   - src/model/liveWires.ts: the sheet's runs: each pin, and each wire cut where things join it. A wire run's current is the sum of what the pins beyond it take (a net's wires as a tree; what does not balance goes out through a power port or a net label). Checked on the simulation demo: the currents balance at every joint.
   - src/app/liveSim.ts: the run, stepped at every frame under a time allowance; the sheet's circuit made again when the sheet changes; the speed (circuit seconds a second) chosen so that the eye can follow; the overlay (colour by voltage, dots by current, the read-out at the cursor).
   - src/app/panels/LivePanel.tsx: Start, Stop, Hold, From the Start, Speed, the colours' scale, the netlist's notes, the parts for a sketch (Konium Designer's own simulation parts and sources, each with the next designator of its kind).
2. (26.182: built and delivered as public, then held back on the day, see 3) What is done by hand, and the scope:
   - A switch and a push button (src/formats/synthetic/simLib.ts: SWITCH, PUSHBUTTON): two display modes, open and closed, each with its own contacts and pins, so the picture is the state. The netlist reads the mode as a resistance (On Resistance 1m, Off Resistance 1G). A click on a switch throws it (an undoable change to the sheet); a push button is closed while the mouse is held on it and leaves the file as it was. A press anywhere on either counts (SchEditor.liveHit).
   - The part selected, in the panel: its values by its model's kind (liveFields), each a box (Enter) and a slider that turns it from a tenth to ten times while held; a slider's whole turn is one step to undo (setLiveField). The value's record is found by simParamHolder (the model's own parameter, or the part's where the model says '*').
   - The Live Scope (panel liveScope, at the bottom; src/app/panels/LiveScopePanel.tsx): a click on a wire, a pin or a two-pin part is the probe (its net's voltage and that run's current; across and through a two-pin part), marked on the sheet; Keep holds up to six. Every step's signals are kept in a ring (src/sim/liveRecord.ts: every net's voltage and every pin's current of a circuit up to 512 signals, else the probes' own), so a probe has its past from the moment it is taken. Views: against time (the last five seconds of the user's time, volts left, amperes right, with the least, most and how often it repeats), spectrum (of all the ring holds, a Hann window, 4096 points), frequency response (an AC sweep of the same netlist from 0.1 Hz to 100 MHz, gain and phase with the 3 dB points, taken again at every change).
   - Added on 15 Nov while this build was in the making (live monitoring of voltage and current at any point, several oscilloscopes reading different points, and a palette of the most used parts shown graphically):
     - Monitors: the probe and every kept probe has its voltage and current read out beside its ring on the sheet (liveMonitors, drawn in the overlay). A probe is kept from the scope (Keep) or from the sheet's right-click menu (Monitor Here: on the sheet only; Add to the Scope; View in a New Scope; Stop Monitoring Here: commands live.*WithContext, first in CONTEXT.sch, shown only on a point that reads). Up to 24 (MAX_KEPT); a sheet's monitors stay for its next run.
     - Scopes: up to six side by side in the Live Scope panel (ScopeState.scopes, each with its own view and probes; + and × on a scope's bar; the one picked takes the next probe, and moving on keeps what the probe was showing). A scope with little room keeps its key to two readings (a container query).
     - The palette: the parts as tiles with their symbols (SymbolPreview of the library's own records), by kind: Passive, Diodes, Transistors, Amplifiers, Sources, Wiring. New in Simulation Parts.SchLib for it: SCHOTTKY (1N5819), ZENER (1N4733A), NJFET (2N5457) and OPAMP_IDEAL (a three-pin op-amp, built-in subcircuit OPAMP_IDEAL.ckt: 100k gain, 10 Hz pole, swings to 15 V either way).
   - The run ends when its sheet is closed; the netlist's notes are capped at six in the panel.
3. (26.183: built as public, superseded the same evening by 26.184, see 4) The kit, the values, the keys and the examples. 26.182 was on the right track and not yet releasable (15 Nov). What the simulator it is modelled on has, and Live Simulation had not: many sources and outputs, each with its properties to set (a sine generator's frequency, span and bias, and so for every one of them); many more components, again with their parameters (a diode's Vf); convenient keys while drawing; and circuits ready drawn to start from. The simulator's source (a public GPL copy, read locally) was gone through for what it offers: its Add menu's groups, its keys, each element's editable fields and its list of circuits. Nothing of it is in Konium Designer: no code, no circuit file, no text. The parts are Konium's own symbols and subcircuits, the examples its own drawings of the standard circuits.

## R20 (STAGE = 20): public from 26.195 (built from 26.191 to 26.194)

Planned on 17 Nov: the AI part in steps, in two parts that both rest on a frontier model: a layout planner and a smart router; and, from a hand-drawn board whose tracks curve round its pads with none of them parallel, the question whether a layout could ever be routed like that, as an option in the settings, for what it gives high-speed and RF circuits.

One principle throughout: the model decides, the engine measures and draws, and the checks are the real design rule check. A model is good at what belongs with what and why, and poor at coordinates, so it is never asked for one. Every job is started by hand, on the model chosen in Preferences › System › AI, and says what it will send first, as the other AI tools do.

The steps:

1. (26.191) Layout planner, the plan: the model reads the board as text and answers with groups, where each goes, what sits at which edge, what must be near which pin, what must be kept apart or clear, each with its reason. Shown as a list and as zones over the board; the zones can be made rooms. Nothing is moved.
2. The placer: carries a plan out exactly (the parts at the edges first, each group's main part in its zone, what must be near a pin at that pin, the rest by their connections, nothing overlapping, everything on the board and clear of holes and keepouts), reports each constraint as met or not with its distance, and a second round lets the model see the result and the designer's remarks.
3. Smart router, the plan: net classes, the order nets are routed in, their layers, widths, vias and pours, written as real net classes and design rules on the board; the autorouter carries it out in that order; the design rule check runs; what failed goes back to the model for another round.
4. The free-flowing routing style of the picture: each route an elastic band pulled tight, every bend an arc concentric with what it passes, saved as tracks and arcs. A style beside 45°, 90° and any angle, for a board or a net class, used by the smart router, the autorouter and a command that reshapes existing routes; interactive routing in that style last. What may be claimed for it: shorter tracks, less crosstalk (tracks spread out and do not run parallel at their least spacing), no corner discontinuities at microwave frequencies, less fibre-weave skew on fast pairs, fewer cracks on flex. What may not: that 45° corners hurt ordinary high-speed digital.
5. Plan, place, route and check as one run with a stop at each stage; the User Guide's section, the website, What's New, STAGE = 20.

## R21 (STAGE = 21): the parts library (planned; built from 26.197)

Planned on 19 Nov: a parts library that is not part of Konium Designer but online, filled by all its users. What is settled:

- The model reads and decides (the pin table, the package, its dimensions, each with the page it came from); Konium's generators draw. As in R20, no drawing comes from the model.

Step 4 as built (26.204): company libraries.
