# Since the last public release (26.099, R2)

Any build may go public, so each build's What's New entry (public/whats-new.json, under the
build's version) sums up every build since the last public one; the entry moves to the next
version with each build. Each build adds its changes here too; when a build goes public this
list starts again.

Release stages (from 26.097; docs/RELEASES.md): every build carries all of Konium, but a feature
is switched on only from the public release it belongs to (src/core/release.ts: STAGE), and shown
as planned until then. R1 (26.097, public): the Design Adviser, Draftsman, AD's ActiveBOM format,
creepage round cutouts, routing at any angle. R2 (26.099, public): Signal Integrity, multi-board, harness. R3 (26.100): BOM
supply, cost, checks and AI part numbers. R4: diagrams. R5: Route Guide, Pin Swapping, enclosure. R6 (26.139, in place of 26.138): requirements.
R7 (26.141; public as 26.142): version control and team projects, Git in place of SVN.
To do (from the next build on): the app's name in its text always "Konium Designer", never "Konium" alone (Get Konium, Support Konium and the rest). "Konium" stays where it names the wider brand: the Konium service, the Konium Dark theme, konium.app, file names such as Konium-26.123.html.
Each later release's What's New entry is drafted in docs/RELEASES.md, and adds the fixes made by then.

## 26.203 (not public: approval in the world parts library, R21 step 3)

- The rules, as built (cloudflare/library/README.md has the table): a word is about one revision; one word of each kind from each contributor; its author can neither confirm a part nor report a problem with it (a fault is put right by publishing again), but may say a board works; Confirmed takes two checks by others; Proven takes that and one board; two people's problems make it Unverified again whatever it was, so that its author can publish the next revision; a new revision starts the lists again. - The service: `POST /check`; the note's lists (`checked`, `built`, `problems`: who, shown name, when, the line) in `library.json`, committed alone (the part's three files stay as published, so a look-up still gets the part whole at the last commit); the store's row keeps the lists beside the note (`more`); a problem's line is put on one line and into the commit's message with the marks a repository's site reads written wide.

## 26.196 (not public: saves that can't be written, large attachments on bug reports)

From a bug report filed against 26.195 (an Allegro board imported and edited, saved as a .PcbDoc that the desktop software then opened showing nothing; the diagnostics showed three "Save failed: a requested file or directory could not be found" in a row).

- What the report most likely was: the browser could not write the file. The system's file selector makes the file (empty) when a name is chosen; the browser then writes a temporary file beside it and swaps it in at the end. When that step fails (security or sync software holding the temporary file back, a folder path too long for the temporary file's name), the empty file stays, and it opens in the desktop software as an empty board. Konium said "Save failed" only in the status line's note, which goes after six seconds. The compound file Konium writes for a board of that size (50 MB with the kept Allegro file, DIFAT sectors) reads clean in an independent reader, strictest setting; 26 Allegro boards from 0.3 to 56 MB import with every object inside the sheet. **Not confirmed with the desktop software from here**: that an empty .PcbDoc opens as an empty board without a word, and that a large Allegro import opens there, are for a trial on the user's side.
- src/platform/fs.ts: `writeHandle` (every document save goes through it): a failed write drops the stream and takes away the file if it is empty; `saveFileAs`: the place chosen can't be written, so the file is downloaded and a window says so (what the browser reported, where the file is, what usually causes it, and whether an empty file may be left); `saveFile` (the document's own file): a file that has gone is asked for again through the file selector, any other failure downloads the document and leaves it unsaved; `writeInto` cleans up the same way. The project file's save uses `writeHandle`.
- src/app/actions.ts `cmdSave`: a save that failed is said in a window (Not Saved), not only in the status line; "Saved" is not said for a document that was only downloaded.
- src/app/diagnostics.ts: the last ten files saved (name, size, how they went out) go in a report's diagnostics, so a report shows whether a save went through.
- Bug reports with large attachments (the reporter could not attach files over 10 MB). In the app (src/platform/report.ts, the dialog): attachments over 8 MB together are zipped (`packFiles`; board files come to a quarter of their size or less), 40 MB zipped at most, 400 MB before zipping; the report goes first, then the zip in parts of 6 MB (`sendReport`, three tries a part); should the parts fail the report has still gone and the person is told. In the report Worker (cloudflare/report): the form's `bulk` field names the zip, the report's text lists it, the answer carries a pass (HMAC under the repository token, half an hour, that report, that many parts); a part posted to `/api/report?part=k&id=…&d=…&t=…` is passed on to GitHub's Contents API as it came (the app makes the request's JSON), so a part costs the Worker next to no memory or processor time; it lands beside the report as attachments.zip.001 and on. The email names the zip and does not carry it.
- **Deploy the report Worker again** (cloudflare/report: `npx.cmd wrangler deploy`). Until then a report with large attachments goes without them and the app says so; smaller reports are as before. The Worker's part could only be tried with a stand-in for GitHub here.
- The reports repository grows with the zips (GitHub asks for under about 1 GB): old ones want deleting now and then.

## 26.173 (R16 in the making: thermal analysis; not public, no What's New entry)

The second part of stage 16, on the same solver: the board's temperature. Carried on build after build until the stage can be released.

- src/analysis/thermal.ts: the whole board (its outline less its cutouts) under a grid, a node for each cell on each copper layer. Along a layer: the copper that crosses from cell to cell (every net's, drawn at three times the grid's fineness; 390 W/m·K) and the laminate that goes with the layer (0.8 W/m·K along the board). From layer to layer: the laminate (0.3 W/m·K through) and the plated walls of the vias and holes in the cell. From the two faces to the air: a coefficient times the cell's area, as a conductance to zero (pcg.ts takes a `shunt` now), the sum done in degrees above the air. Still air is worked out: convection by the simplified laminar relations for air, h = C·(ΔT/L)^¼ with C 1.32 face up, 0.59 face down, 1.42 upright (checked against two published statements of them; L is 4A/p lying flat, the longer side upright), radiation ε·σ·(Ts² + Ta²)·(Ts + Ta) at 0.9, from each face's mean temperature, and the sum repeated until the coefficients settle (twelve times at most). A part's dissipation goes in at its pads, by pad area; its junction is the board under it plus power times a junction-to-board resistance, where one is given. Every component is given the board's temperature at its pads.
- The copper's own heat: a power analysis's loss in each link put in at the link's ends (copperHeat), and the board's temperature given back to the power analysis (PowerSetup.field: each link's conductance scaled to the temperature of its place). app/thermalRun.ts works the two turn about until the hottest place moves by under 0.2 K, four turns at most.
- Warm-up (warmUpSteps): the settled analysis's heat and coefficients, each node's heat capacity (copper 3.45 MJ/m³·K by its cover, laminate 2.0), implicit steps that lengthen by a fifth each, from a two-hundredth of the board's lumped time constant: the hottest place and each heated part against time, the times to half and nine tenths of the rise. - src/analysis/thermalMap.ts, app/thermalRun.ts, app/panels/ThermalPanel.tsx: Tools › Thermal Analysis... ## 26.172 (R16 in the making: power analysis; not public, no What's New entry)

The aim: thermal and EMC analysis as deep as is feasible, and later the emission of boards with antennas. - src/analysis/pcg.ts: a network of conductances solved for its node potentials (some nodes held, flows put in at others; nodes with no path to a held node get none).
